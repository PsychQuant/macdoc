## Context

ooxml-swift has two parallel serialization implementations for `word/document.xml`:

- **Authoring path**: `DocxWriter.writeDocument` renders a Swift string template and concatenates typed-model `toXML()` output.
- **Transcoder path**: `ReverseExtractor` derives typed ops from the tree; the reducer + `XmlTreeWriter` rebuild the part and a byte-equal trial gate proves the rebuild.

Since tree-first IO v1.0 (task 6.2), `retreeXMLParts` round-trips every typed-writer-produced part through `XmlTreeReader.parse → XmlTreeWriter.serialize` before packaging, so both paths already terminate in the same serializer. The remaining divergences are pure tree content:

1. The `writeDocument` template emits newlines between elements (after the root open tag and after the `<w:body>` open tag). `ReverseExtractor.elementsOnly` treats whitespace-only text nodes as foreign forms (`Unsupported("non-element-content")`) by design — the reducer stamps compact element-only structure.
2. No authoring creation site fills `Paragraph.w14ParaId` (the field and its emit path exist since v0.20.3), and the create-from-scratch root fallback declares only `xmlns:w` + `xmlns:r`. `extractParagraph` hard-requires paraId because it is the stable `setRuns` addressing key across script round-trips.

Both blockers are individually fatal: `documentUpgrade` is all-or-nothing, so authoring documents always land in the raw carry channel (`dsl_ratio = 0`). Downstream, every che-word-mcp self-authored document has an unreadable, uneditable script export (PsychQuant/che-word-mcp#173).

Existing registered vocabulary that constrains this design (word-canonical-forms, #131):

- `ReverseExtractor.authoringDefaultRootAttributes` = minimal `xmlns:w` + `xmlns:w14` — a source root matching it needs no `setDocumentRoot` op; anything else is absorbed by an explicit `setDocumentRoot` op and still upgrades.
- Prolog variants are absorbed by `setDocumentProlog` (real Word CRLF prologs already upgrade to 100% DSL on the `90_template_ja.docx` baseline).

## Goals / Non-Goals

**Goals:**

- Pure-paragraph documents built through the authoring API reverse-extract to `channel: dsl` and round-trip byte-equal (export → execute → identical `word/document.xml` bytes).
- All byte-level changes stay on the authoring side; the transcoder's strictness is the fixed contract being conformed to.
- New paragraphs created through authoring APIs carry a Word-plausible `w14:paraId`; parsed content keeps its source state untouched.

**Non-Goals:**

- Rich tables, styled cells, hyperlink extraction, or any widening of the extractor's canonical DSL subset (tracked as PsychQuant/ooxml-swift#86, existing "later Phase 4 iterations" roadmap).
- Loosening any transcoder gate (`elementsOnly` strictness, paraId requirement, byte-equal trial, `authoringDefaultRootAttributes`). Rejected because synthesizing paraIds or normalizing whitespace at compare time breaks the byte-equal round-trip proof.
- Backfilling paraId onto paragraphs parsed from existing documents (minimal-diff fidelity: opening a legacy document and editing one paragraph must not rewrite every paragraph's attributes).
- Reordering or rewriting the captured-root path of `renderDocumentRootOpenTag` (documents opened from disk keep the existing behavior).
- che-word-mcp pin bump and consumer regression tests (follow-up on PsychQuant/che-word-mcp#173 after release).

## Decisions

### D1 — Fix the authoring emitter, keep the transcoder frozen

The transcoder side defines canonical form; the authoring side conforms. Alternative (relax `elementsOnly` / synthesize paraId in the extractor) rejected: paraId is the `setRuns` addressing key and whitespace tolerance would make the byte-equal trial unsound.

### D2 — Template hygiene only; no XmlTree-based rewrite of writeDocument

Remove the two inter-element newlines from the `writeDocument` template (after the rendered root open tag, after the `<w:body>` open tag). Because `retreeXMLParts` already funnels the bytes through `XmlTreeWriter.serialize`, removing the text nodes is sufficient — no need to port `writeDocument` to build an `XmlTree` directly. Alternative (construct the tree programmatically and serialize) rejected as more invasive with zero additional acceptance value. The prolog line stays as-is (`setDocumentProlog` absorbs it; the writer default prolog `<?xml …?>` + LF is already the canonical no-op form).

### D3 — paraId stamped at authoring chokepoints, generated by an injectable per-document generator

Stamping sites: `appendParagraph(_:)`, `insertParagraph(_:at: Int)` (both in the typed-model Document API) and `insertParagraph(_:at: InsertLocation)`. Rule: if the incoming `Paragraph.w14ParaId` is nil, stamp a generated value; a caller-supplied value is kept verbatim. Reader-parsed paragraphs never pass through these APIs on load, so absent stays absent.

Generator contract (`ParaIdGenerator`):
- Output: 8 uppercase hex characters (Word convention), numeric value in the open interval (0x00000000, 0x80000000) exclusive — Word's documented validity range.
- Uniqueness: regenerates until the value collides with no existing `w14ParaId` in the target document (collision scan over body paragraphs).
- Injectable seed/source so tests can pin deterministic sequences; production default uses `SystemRandomNumberGenerator`.

Alternatives rejected: `Paragraph.init` default (reader also constructs via init — source-absent paragraphs would gain phantom IDs, breaking verbatim fidelity and making every transient Paragraph nondeterministic); `DocxWriter` save-time backfill (cannot distinguish authored-new from parsed-without-paraId, so editing one paragraph of a legacy file would rewrite all paragraphs).

### D4 — Create-from-scratch root emits the full Word-canonical namespace cloud

The empty-`documentRootAttributes` fallback emits the complete real-Word root attribute set — every `xmlns:*` declaration plus `mc:Ignorable` — captured verbatim (values and order) from the `90_template_ja.docx` baseline's `document.xml` root, stored as an ordered constant in DocxWriter (not hand-typed from memory; the constant's provenance is asserted by a test that parses the fixture where available). The fallback path bypasses the dictionary-sorting `renderDocumentRootOpenTag` ordering and emits the constant's order directly, so the root tag is byte-identical to Word's.

Consequences, accepted deliberately (user decision at discuss): exported scripts of self-authored documents always carry one `setDocumentRoot` op (the cloud differs from the minimal `authoringDefaultRootAttributes`); that op lists ~20 namespace attributes. DSL upgrade and byte-equal are unaffected — `setDocumentRoot` absorbs any attribute set.

Alternatives rejected:
- Minimal `xmlns:w` + `xmlns:w14` (aligning with `authoringDefaultRootAttributes`, zero-op scripts): drops `xmlns:r`, so any create-from-scratch document containing `r:id` references (hyperlinks, images) would become namespace-invalid — a concrete regression for existing consumers.
- Minimal-valid `w + r + w14`: avoids the invalidity but still differs from the registered minimal default (same one-op script cost as the full cloud) while buying none of the Word-imitation value.
- Updating `authoringDefaultRootAttributes` / `emptyAuthoringDocument` to match the new cloud: touches the transcoder vocabulary, violating D1.

### D5 — Spec delta lands in ooxml-script-transcode

The canonical form is defined by that capability; the new requirement states the conformance obligation next to the contract it conforms to. Alternative (new capability, or delta on ooxml-tree-io) rejected: splits normative text away from the canonical-form definition for a 3–4 file fix. Companion delta: `ooxml-roundtrip-fidelity` already pinned the create-from-scratch root fallback to the minimal `w + r` set (scenario "Create-from-scratch document emits minimal namespace set"), so D4 requires a MODIFIED delta there — the fallback paragraph and scenario now specify the full Word-canonical cloud; the captured-attributes round-trip behavior is untouched.

## Implementation Contract

**Observable behavior after the change:**

1. Build a document via `WordDocument` authoring APIs (create-from-scratch, append/insert paragraphs with plain or formatted runs), save via `DocxWriter`, run `ScriptTranscoder` export: the coverage report shows `word/document.xml` with `channel: dsl` and the aggregate `dsl_ratio` reflects the part upgrading (for a pure-paragraph fixture, document.xml per-part ratio is 1.0).
2. Executing the exported script rebuilds a docx whose `word/document.xml` bytes equal the source's exactly (existing execute→byte-equal harness passes on the new fixture).
3. `word/document.xml` of a saved authoring document contains no whitespace-only text nodes between elements; its root tag carries the full Word-canonical namespace cloud when the document was created from scratch; every paragraph appended or inserted through the authoring API has `w14:paraId="XXXXXXXX"` (8 uppercase hex).
4. Round-tripping an existing document that lacks paraIds (open → save without paragraph edits) does not add paraId attributes anywhere.
5. A paragraph inserted with a caller-preset `w14ParaId` keeps that exact value; two paragraphs inserted into the same document never receive the same generated value.

**Interface / data shape:**

- New public type `ParaIdGenerator` (packages/ooxml-swift/Sources/OOXMLSwift/Models/ParaIdGenerator.swift): generates 8-uppercase-hex strings in (0, 0x80000000) exclusive, seedable/injectable RNG for tests, uniqueness enforced against a provided set of existing IDs.
- `appendParagraph(_:)` / `insertParagraph(_:at:)` (Int and InsertLocation overloads) keep their signatures; stamping is an internal behavior change (nil paraId → generated, non-nil → preserved).
- DocxWriter gains an ordered full-cloud root constant used only when `documentRootAttributes` is empty; `renderDocumentRootOpenTag`'s captured-attributes path is unchanged.

**Failure modes:**

- ParaId generation failure is not an expressible state (regenerate-on-collision over a 2^31 space; no throwing surface added).
- Documents authored by writing `body.children` directly (bypassing the chokepoint APIs) get no stamping — their export falls back to the raw channel exactly as today. Intentionally out of contract; the report's existing `paragraph-no-paraId` naming already diagnoses it.

**Acceptance criteria:**

- New test target Tests/OOXMLSwiftTests/AuthoringCanonicalConformanceTests.swift covers observable behaviors 1–5 above (reverse-to-dsl, byte-equal round-trip, no-backfill, preset-preserved, uniqueness, root-cloud shape, no inter-element whitespace).
- Full existing ooxml-swift test suite passes; any golden/snapshot fixtures asserting old authoring bytes (2-namespace root, pretty-printed document.xml, paraId-less paragraphs) are updated in the same change with the reason recorded in the commit.
- `spectra validate` passes; release notes flag the two byte-level behavior changes (root cloud, paraId stamping).

**Scope boundaries:** in scope — pure-paragraph canonical conformance of the authoring path in packages/ooxml-swift; out of scope — extractor subset widening (#86), che-word-mcp consumer work (#173), captured-root reordering, prolog changes.

## Risks / Trade-offs

- [Residual tree divergence beyond the three known deltas (e.g., an unnoticed template artifact) keeps the byte-equal gate failing] → The gate's `byteMismatchLocator` names the first divergent byte with context windows; the round-trip test surfaces it immediately, and fixes stay template-side per D1.
- [paraId stamping changes all authoring output bytes; downstream golden tests break] → Called out in proposal as behavior change; downstream refresh is mechanical and the release notes make the byte diff expected. che-word-mcp regression waits on #173.
- [Full-cloud constant drifts from the fixture it claims to mirror] → Provenance test parses `90_template_ja.docx` (skips cleanly when the local-only fixture is absent, mirroring the existing `.note` XCTSkip pattern) and asserts constant equality.
- [Random paraId makes some future byte-level test flaky] → Generator is injectable; tests that need stable bytes pin a seeded generator or preset explicit IDs. The export→execute round-trip is immune (IDs ride in the script).
- [Two authoring root defaults now exist conceptually (reducer seed w+w14 vs DocxWriter full cloud)] → Documented in the spec delta: the reducer seed is the script-execution baseline, the writer cloud is the create-from-scratch surface; the `setDocumentRoot` op bridges them explicitly, so neither is ambiguous at runtime.

## Migration Plan

1. Land generator + stamping + template/root changes with the new conformance tests in packages/ooxml-swift (single change, no feature flag — the behavior change is the fix).
2. Update in-repo fixtures/goldens that encoded the old bytes.
3. Tag an ooxml-swift release; release notes list the two byte-level changes.
4. Follow-up (out of this change): PsychQuant/che-word-mcp#173 bumps the pin, refreshes consumer goldens, adds an MCP-level export_script regression; PsychQuant/ooxml-swift#86 proceeds against the now-conformant baseline.

Rollback: revert the ooxml-swift commits; no persisted-data migration exists (documents produced meanwhile remain valid Word files either way).
