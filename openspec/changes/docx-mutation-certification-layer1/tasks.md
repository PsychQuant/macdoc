## 1. Mutation intent

- [x] 1.1 Mutation intent is derived from a closed step-type table. `MutationIntent.derive(from:)` returns the union of the table rows for runtime-functional steps; pending steps contribute nothing; an unlisted functional step type throws `CertificationError.intentUnavailable(stepType:)`. Implements the design decision "Derive allowed parts from step types through a closed table". Verified by `MutationIntentTests` covering every row of the spec's "Allowed-part derivation" example and the unknown-type failure, written RED first.

## 2. Layer 1 gate

- [x] 2.1 [P] Layer 1 gate proves package and byte preservation — part-set and byte checks. `Layer1Gate.evaluate` reports `partAdded`, `partRemoved`, and `unexpectedChange` with both sizes and the first differing offset. `changedParts` lists every differing part. This follows the design decision "Compare non-target parts by exact bytes, not canonical XML". Verified by `Layer1GateTests` cases for a clean pass, a dropped theme part, an added part and an unallowed `word/styles.xml` change, all written RED first.
- [x] 2.2 Layer 1 gate package-integrity checks. The candidate must re-open through `DocxReader` (`unreadablePackage`). Every `.xml` and `.rels` part must be well-formed (`malformedXML`). `[Content_Types].xml` must cover every part through an `Override` or an extension `Default` (`missingContentType`). Every internal relationship target must exist (`danglingRelationship`). Verified by one `Layer1GateTests` case per violation, each built from a synthetic package.

## 3. Certificate

- [x] 3.1 [P] Certificate claims only evaluated layers. `CertificationCertificate` is `Codable` with `schemaVersion` 1. `status` is `layer1Verified` or `rejected` and never `certified`. `layer2` and `layer3` are `notEvaluated` with a non-empty reason. The `verify` outcome is `passed`, `failed` or `notRequested`, and the certificate carries hashes, allowed and changed parts, URLs and a timestamp. This follows the design decision "Certificate claims only the layers that were evaluated". Verified by `CertificateTests`: a JSON round-trip, a check that the status vocabulary cannot encode `certified`, and a check of the key names.

## 4. Certified transaction

- [x] 4.1 Certified transaction commits only after every gate passes. It writes the candidate in the output directory and renames it onto the output only on success; on failure it renames the candidate to `<output-stem>.rejected.docx` and leaves the output path byte-identical. This follows the design decisions "Place the certified transaction at the workflow boundary, not inside OOXMLSwift apply" and "Write the candidate next to the output and keep a rejected candidate for diagnosis". Verified by `CertifiedTransactionTests`: a success case (output written, no leftovers) and a gate-failure case (a pre-existing output is unchanged and the rejected file holds the candidate bytes).
- [x] 4.2 The manifest `verify` assertions run against the candidate before commit. A verify failure throws `CertificationError.verifyFailed` and never creates the output. Verified by a `CertifiedTransactionTests` case whose `expected_paragraphs_min` is unmet while the output path did not exist beforehand.
- [x] 4.3 Guard the baseline against change between read and commit. The baseline SHA-256 recorded at read time is recomputed before the rename, and a mismatch throws `CertificationError.baselineChanged` with the output untouched. Verified by a `CertifiedTransactionTests` case that uses an internal test hook between the gate and the commit to rewrite the baseline.

## 5. CLI

- [x] 5.1 docx apply commits its output only through the certified transaction, and gains `--certificate <path>`, written on success and on failure. On failure, stderr names the failure kind and the rejected-candidate path, and the exit code is non-zero. Verified by two `MacDocDocxIntegrationTests` cases: `--certificate` producing a `layer1Verified` JSON on success, and a failing `verify` leaving `out.docx` absent.

## 7. R2 — adversarial review fixes (review-c137.md)

- [x] 7.1 CRITICAL (Finding 1): a certificate-write failure must never overwrite the transaction's own success/failure signal. Two layers: (a) pre-flight validation of the `--certificate` destination (parent directory exists and is writable, destination itself is not a directory) before anything is written, throwing `CertificationError.certificateDestinationInvalid(path:reason:)`; (b) a write that still fails after that check passes (a race) is reported only through a new `certificateWarnHandler` callback and never changes `apply`'s return/throw outcome. This is one half of spec.md's Requirement "Pre-flight destination checks reject an unwritable output or certificate path before any write" (the other half is task 7.2) plus the whole of "A certificate write failing after pre-flight validation passed does not change the transaction's own result", implementing the design decisions "R2: Pre-flight checks reject an unwritable output or certificate destination before anything is touched" and "R2: A certificate write failing after pre-flight validation passed does not change the transaction's own result". Verified by `CertifiedTransactionTests` (destination invalid against a would-succeed and a would-fail-verify manifest; the write-race against a would-succeed and a would-fail-verify outcome, via the new `testHookAfterCommitBeforeCertificateWrite` seam) and by `MacDocDocxIntegrationTests` (destination invalid against both outcomes at the CLI), all written RED first.
- [x] 7.2 MEDIUM (Finding 2): an output path that already exists and is a directory must be rejected before any write, not silently deleted by `FileManager.replaceItemAt`. New `CertificationError.outputPathIsDirectory(path:)`, checked in the same pre-flight step as 7.1. This is the other half of spec.md's Requirement "Pre-flight destination checks reject an unwritable output or certificate path before any write". Verified by a `CertifiedTransactionTests` case and a `MacDocDocxIntegrationTests` case, each confirming the directory and its contents survive intact, written RED first.
- [x] 7.3 LOW cleanup, bundled:
  - L1: `Manifest.swift`'s `Step` enum header comment corrected — it grouped 8 cases as "Phase 1 runtime-functional" though only 4 (`insertParagraph`/`removeParagraph`/`setBold`/`wrapLink`) actually are, per `EditPlanner.swift` and `MutationIntent.isRuntimeFunctional`. Documentation only, no test.
  - L2: `Layer1Gate`'s `[Content_Types].xml` `Default` `Extension` matching made case-insensitive (OPC, ECMA-376 Part 2: the Content Types stream's `Default` element). Verified by `Layer1GateTests.testContentTypeDefaultExtensionMatchIsCaseInsensitive`, written RED first.
  - L3: relationship `Target` percent-decoded before resolution. Verified by `Layer1GateTests.testRelationshipTargetIsPercentDecodedBeforeResolution`, written RED first.
  - L4: dedicated `../` relative-target test pair added (positive: resolves to an existing sibling-directory part; negative: reported dangling when that part is absent, proving the traversal is exercised). ## 8. R3 — second-round adversarial review fixes (review-c137-r2.md)

- [x] 8.1 CRITICAL (Finding A): a `--certificate` destination that refers to the same file as the output, the baseline, the rejected-candidate path, or the manifest argument must be rejected before any write — writing the certificate there (which happens after the commit) would otherwise silently overwrite the just-verified output or the caller's own source file while `apply` still reported success. New `CertificationError.certificateDestinationConflictsWithOtherPath(certificatePath:conflictingRole:conflictingPath:)` and new public `CertifiedTransaction.filesAreIdentical(_:_:)` (string-normalization tier, then a device/inode tier when both paths exist — covers hard links and a case-insensitive filesystem's collision once either file exists). `CertifiedTransaction` checks the output, baseline and rejected-candidate paths; the CLI layer checks the manifest path (the one path `CertifiedTransaction` never sees) using the same public method before ever calling `apply`. Implements the design decision "R3: Certificate destination must not collide with another path this transaction uses". Verified by `CertifiedTransactionTests` (output/baseline/rejected-candidate conflicts, plus a hard-link variant proving the device/inode tier actually runs) and by `MacDocDocxIntegrationTests` (output/baseline/manifest conflicts at the CLI, each confirming the colliding file's bytes survive byte-for-byte), all written RED first.
- [x] 8.2 MEDIUM (Finding B): the output-is-directory pre-flight check (task 7.2) left a TOCTOU window between itself and the final commit rename — `FileManager.replaceItemAt` still silently deleted a directory that appeared in that window, with no warning mechanism at all. Fixed not by adding a second check but by replacing the primitive: `commit(from:to:)` now uses POSIX `rename(2)` (`Darwin.rename`), which refuses a directory destination with `EISDIR` instead of deleting it. On that failure the candidate — which already passed every gate — is preserved at the rejected-candidate path (or, if that rename also fails, left at its own temporary path) and new `CertificationError.commitFailed(path:reason:rejectedCandidatePath:)` is thrown. Implements the design decision "R3: Commit uses POSIX rename(2), not FileManager.replaceItemAt, so a directory destination is refused instead of deleted". Verified by a `CertifiedTransactionTests` case that reproduces the review's own probe (a directory injected via the existing `testHookBeforeBaselineRecheck` seam, between pre-flight and commit), confirming the directory and its contents survive and the candidate is preserved at the rejected path, written RED first.
- [x] 8.3 LOW cleanup, bundled:
  - Finding C: `Layer1Gate`'s `hasContentType` made the `Override` element's `PartName` attribute comparison case-insensitive too, matching the `Default` element's `Extension` comparison task 7.3/L2 already fixed — OPC's part-name comparison is the same rule either way. Verified by `Layer1GateTests.testContentTypeOverridePartNameMatchIsCaseInsensitive` (removes the generic `xml` `Default` fallback first, matching how the review's own probe exposed the gap), written RED first.
  - Finding D (test-gap half): added `Layer1GateTests.testContentTypeDefaultExtensionMatchIsCaseInsensitiveOnTheQuerySide`, which fails if `hasContentType`'s read-side `.lowercased()` call is removed (verified by a manual mutation check: removed the line, confirmed the new test fails, restored the file and confirmed byte-identical via `cmp`) — the existing case-insensitivity test only exercised the write side, since every fixture part's own extension was already lowercase.
  - Finding D (CLI test-gap half, mutation M6): added `MacDocDocxIntegrationTests.testCertificateWriteFailureAfterSuccessfulCommitStillExitsNonZero`, closing the docx-workflow-cli spec's "Certificate write failing after a successful commit still exits non-zero" Scenario's complete lack of CLI-level automated coverage. Uses a certificate destination directory with permissions `0600` (write bit set, search/execute bit cleared): `FileManager.isWritableFile` (pre-flight's own check) reports it writable — verified empirically with `touch`/`open()` — but any real attempt to create a file inside it fails with `EACCES`, giving a deterministic, non-racy reproduction of "pre-flight passed, the real write still failed" without timing-dependent concurrency.
  Verified overall by `spectra analyze`/`validate` staying clean (run against a `.git`-free sandbox copy, not the shared worktree) and both full test suites passing 0 failures (see the R3 section of the implementation report).

## 9. R3b — residual gap from R3's own fix (post-review follow-up)

- [x] 9.1 CRITICAL variant of Finding A, reintroduced by case-insensitivity: task 8.1's `filesAreIdentical` pre-flight check cannot see a collision between the output and the certificate destination when the two differ only by case and NEITHER exists yet, because its device/inode tier requires existence. On a case-insensitive filesystem (APFS's default), `--output Out.docx --certificate out.docx` (both absent beforehand) passes pre-flight, commit creates `Out.docx`, and the certificate write that follows silently overwrites it with certificate JSON while `apply` still reports success. Fixed by re-running `filesAreIdentical` a second time — against the output, baseline, and rejected-candidate paths — immediately after commit and immediately before the certificate write, when the output (or rejected-candidate path) is guaranteed to exist and the device/inode tier is therefore live. A hit routes through the existing `certificateWarnHandler` mechanism from task 7.1 rather than a new `CertificationError` case, since the transaction's own outcome (the commit already happened) is unaffected. Implements the design decision "R3b: re-check the certificate destination against the just-committed paths immediately before writing it", and closes the residual limitation task 8.1/8.2's own Risks/Trade-offs entry had recorded as unclosed. Deliberately does NOT query volume case-sensitivity attributes (`.volumeSupportsCaseSensitiveNamesKey`) — the re-check works by observing the real filesystem after commit, so it does not need to predict case-folding ahead of time. Verified by two tests, each written RED first against the pre-fix code (confirmed: `certificateWarnHandler` never called, and the output file's bytes became certificate JSON instead of a ZIP container), then GREEN against the fix, with byte-identical restoration of the pre-fix file confirmed via `cmp` before re-confirming GREEN:
  - `CertifiedTransactionTests.testCertificateDestinationCollidingWithOutputOnlyByCaseIsCaughtAfterCommit` (library level).
  - `MacDocDocxIntegrationTests.testCertificateDestinationCollidingWithOutputOnlyByCaseIsCaughtAfterCommit` (CLI level).
  Both tests detect a case-insensitive filesystem empirically (create a mixed-case file, check whether its lowercased path resolves to it) and `XCTSkip` with a stated reason on a case-sensitive filesystem, per explicit instruction to avoid querying volume attributes.
  Verified overall by `spectra analyze`/`validate` staying clean (run against a `.git`-free sandbox copy) and both full test suites passing 0 failures (see the R3b section of the implementation report).

## 10. R4 — third-round adversarial review fixes on R3's own primitive swap (review-c137-r3.md)

- [x] 10.1 HIGH (Finding E): R3's switch from `FileManager.replaceItemAt` to POSIX `rename(2)` (task 8.2) changed behavior for a case nobody had checked: when `--output` itself is a symbolic link to an unrelated file, `rename(2)` replaces the symlink's own directory entry instead of following it — the alias relationship the caller set up is silently severed, the file the symlink used to point to is left completely untouched and now out of sync, and `apply` reports success (exit 0, `layer1Verified`) where the pre-R3 primitive threw and touched nothing. New `CertificationError.outputPathIsSymlink(path:linkTarget:rejectedCandidatePath:)`, detected via `lstat(2)` (not `stat(2)`, which would misreport a dangling symlink as absent) at Step 0 pre-flight (`rejectedCandidatePath` `nil`) and again immediately before the commit rename (candidate preserved at the rejected-candidate path on a hit). The second check narrows, but per the review's own analysis does not eliminate, the TOCTOU window — `rename(2)` has no `EISDIR`-equivalent refusal for a symlink destination, so there is no atomic primitive to switch to the way task 8.2 did for directories; this residual is recorded honestly in design.md's Risks/Trade-offs rather than claimed as closed. Implements the design decision "R4: Reject an output path that is (or becomes) a symbolic link". Verified by two library tests (`CertifiedTransactionTests.testOutputPathThatIsAlreadyASymlinkIsRejectedBeforeAnyWrite`, `.testOutputPathBecomingASymlinkBetweenPreFlightAndCommitIsRejectedAndCandidatePreserved`) and one CLI test (`MacDocDocxIntegrationTests.testOutputPathThatIsASymlinkIsRejectedAtCliAndTargetSurvivesUntouched`), each written RED first against the pre-R4 code — confirmed: `apply` returned success with no error, and a subsequent `readlink`/`destinationOfSymbolicLink` call on the (no-longer-a-symlink) output path failed with `EINVAL`, proving `rename(2)` really had replaced the symlink itself.
- [x] 10.2 HIGH, security-relevant (Finding F): `rename(2)` does not preserve a replaced file's POSIX permissions, ACL or extended attributes the way `FileManager.replaceItemAt` did — every successful overwrite of an existing output silently widens its permissions back to the candidate's own default (process umask) and drops any custom extended attributes, which could silently loosen access to a `.docx` a caller had deliberately locked down (e.g. `chmod 640` on unpublished research). New `preserveMetadataIfOverwriting(candidateURL:outputURL:)`, run immediately before the commit rename only when the output already exists and is not a directory (a no-op for a brand-new output; defers to Finding B/task 8.2's own `EISDIR` handling when the destination is unexpectedly a directory): copies the old output's permissions/ACL/extended attributes onto the candidate via `copyfile(3)` (`COPYFILE_SECURITY | COPYFILE_XATTR`), then restores the candidate's own (pre-copy) modification time — `COPYFILE_STAT` would otherwise also copy the old file's modification time, misrepresenting when the genuinely-changed content was written — while deliberately carrying over the old output's creation date via `FileManager` (unlike modification time). A `copyfile(3)` failure throws new `CertificationError.metadataPreservationFailed(path:reason:rejectedCandidatePath:)` and rejects the commit outright — the candidate is preserved at the rejected-candidate path, never landing with looser access than the file it would have replaced. Implements the design decision "R4: Restore a replaced output's permissions, ACL and extended attributes before committing over it". Verified by three library tests (`.testOverwritingExistingOutputPreservesPermissionsXattrsAndCreationDateButNotModificationTime`, `.testMetadataPreservationFailureRejectsCommitAndLeavesOldOutputUnchanged`, `.testNewOutputWithNoPriorFileIsUnaffectedByMetadataPreservation`) and two CLI tests (`.testOverwritingExistingOutputAtCliPreservesPermissionsXattrAndCreationDate`, `.testMetadataPreservationFailureAtCliRejectsCommitAndReportsError`), each written RED first against the pre-R4 code — confirmed: permissions/xattr/creation date were NOT preserved, and a `copyfile`-failure scenario (existing output at mode `0`) proceeded to commit successfully instead of rejecting.
- [x] 10.3 LOW, test gap (Finding G): task 8.3's Override PartName case-insensitivity fix (Finding C) had its own verification test change only the DECLARED `Override PartName`'s case — the actual on-disk part name it was matched against was already lowercase, so `hasContentType`'s read-side `.lowercased()` call was never exercised (mutation check: removing that line left all 15 `Layer1GateTests` cases passing), the same pattern task 7.3's Finding D test gap had for the `Default` branch. New `Layer1GateTests.testContentTypeOverridePartNameMatchIsCaseInsensitiveOnTheQuerySide`, mirroring `testContentTypeDefaultExtensionMatchIsCaseInsensitiveOnTheQuerySide`'s shape: adds a part with an uppercase on-disk name (`word/Extra.XML`) matched via `Override`, with the generic `Default Extension="xml"` fallback removed so only the `Override` branch can satisfy the lookup. Mutation-verified: removing the read-side `.lowercased()` makes exactly this one new test fail (1 failure out of 16), leaving all pre-existing cases green — confirming the mutation is caught by, and only by, the intended test — then restored (`cmp` byte-identical) before re-confirming all 16 green.
  Verified overall by `spectra analyze`/`validate` staying clean (run against a `.git`-free sandbox copy, not the shared worktree) and both full test suites passing 0 failures (see the R4 section of the implementation report).
